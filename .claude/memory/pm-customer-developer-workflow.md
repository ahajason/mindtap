# PM-客户-程序员三角色协作模式

## 核心概念

项目采用三角色分工协作模式，所有需求沟通和实现通过文档驱动，而非直接对话。

## 角色定义

| 角色 | 对应 | 职责 |
|---|---|---|
| **@Customer** | 用户 | 提出需求、反馈问题、确认方案、验收交付 |
| **@PM** | 产品经理（当前会话的 Claude Code） | 与 @Customer 沟通确认需求，沉淀到文档，交给 @Developer 执行 |
| **@Developer** | 程序员（其他 Agent） | 读取文档实现，更新任务跟踪状态 |

## 文档体系

两份文档分工明确，互不交叉：

1. **`docs/governance/pm-customer-dialogue-prd.md`** — 只有 @PM 可以修改
   - §一 角色定义
   - §二 协作流程 + 沟通验收规范（含验收提示词模板）
   - §三 需求沉淀（版本背景 → 沟通记录 → 代码探查 → 需求条目清单 REQ-xx）
   - §四 参考文档
   - 附录：维护规则 + 结构总览

2. **`docs/plans/developer-task-board.md`** — 只有 @Developer 可以修改
   - 关联文档说明
   - 协作规则
   - 任务跟踪表（REQ-xx，含完成情况 + 备注）

## 沟通交互模式

1. @Customer 提出需求/反馈问题（可能是模糊的、非技术性的）
2. @PM 澄清确认：术语对齐、版本归属、范围边界、主动枚举副作用
3. @Customer 确认/调整
4. @PM 沉淀到文档 §3.2
5. @PM 输出可执行提示词给 @Developer
6. @Developer 实现并更新任务跟踪表
7. @Customer 验收，反馈问题
8. 循环直到验收通过

## 验收提示词格式

验收反馈提示词固定包含：
- 引用 PM 文档和开发者任务跟踪板
- 每个问题：现象描述 → 原因分析 → 修复要求
- 修复方向（多个选项让 @Developer 选择）
- 参考设计文档
- 完成修复后更新任务跟踪表的要求

## 关键规则

- @PM 只做需求确认与沉淀，不做代码实现
- @Developer 只做代码实现与任务跟踪，不擅自变更需求范围
- 需求模糊点先评审再开发
- 所有改动可追溯到业务价值与对应版本的原始设计文档
- 当有 2-4 个离散选项时用 ask 工具让 @Customer 选择
- 有明确默认值的决策直接选择并说明理由
