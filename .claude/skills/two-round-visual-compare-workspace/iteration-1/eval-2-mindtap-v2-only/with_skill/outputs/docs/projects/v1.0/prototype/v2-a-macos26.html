Capture cost optimization

On-device tokenization pushed ingest from 340 ms to 41 ms median, but the OCR pre-pass still dominates on longer notes. Track three more lanes before the v1.2 sprint review.
Updated 14:08 312 words · ~1.9 min read Linked to 4 notes Shared with Mei, Devon

The v1.1 capture pipeline spends 78% of wall time in the OCR pre-pass. Pushing tokenization onto-device took the ingest path from 340 ms to 41 ms median — a 8.3× win on warm cache — but every note longer than 1,200 characters still pays a 220 ms tax before the LLM even sees the prompt.

Treat OCR like an optional pre-flight, not a hard gate. Defer it behind the tap-to-open action, not the type-to-capture action.

We have three lanes left. First, batch OCR per notebook window: a 30-second window collapsed 19 separate calls into 2 with no quality regression on the validation set. Second, swap the on-device tokenizer to the 32k BPE built last month — same accuracy, 14% fewer tokens, which trims the LLM cost line directly. Third, retire the per-keystroke preview render; users only read the final card.

Blocker: the on-device tokenizer doesn't ship in EU builds until the 26.2 entitlement lands. Plan to land lanes 1 and 3 by sprint 4, hold lane 2 for the post-release window.
