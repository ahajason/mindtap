# V0.2.0.x PATCH 验收流程(模板化)— 含 L1/L2/L3 + 编号约定

> **目的**: 锁住 V0.2.0 系列 PATCH 收口的通用验收流程, 让 `V0.2.0.7` / `V0.2.0.11` / `V0.2.0.12` / `V0.2.0.13` / `V0.2.0.14` 及后续 PATCH 验收输出**格式一致、可追溯、可批量回归**。
>
> **强约束**: 验收项编号用 `[类目-序号]`(`A-1` `A-2` `B-2-1` `C-3`), **不用 "了" 句式**(user 明确要求, 见 V0.2.0.14 PATCH L3 重测反馈)。
>
> **范围**: 本文档是 governance 层（跨版本规则），适用所有 V0.2.0.x PATCH；不定义 V0.2.1 及后续 MINOR 的功能路线或验收范围。

---

## 一、验收三层(L1 静态 / L2 dev 实测 / L3 user 重测)

| 层 | 谁跑 | 在哪跑 | 何时跑 | 失败影响 |
|---|---|---|---|---|
| **L1 静态** | agent (Claude) | WSL | commit 前必须 | 禁止 commit |
| **L2 dev 实测** | agent (Claude) | WSL + D:\ | commit 前(系统 API / OS 集成 / 框架 runtime 改动后必须) | 禁止 commit |
| **L3 user 重测** | human (user) | D:\ | agent 集成 + push origin/develop 后 | 禁止 merge 到 main / 禁止下一 PATCH 开工 |

> 任何一层失败 = PATCH 不收口, 重做后再走下一层。

## 二、验收项编号约定(强约束)

### 2.1 编号格式

```
[类目-序号]
```

- **类目** = 大写字母(代表组件 / 交互类型), 跨 PATCH 沿用:
  - `A` = StatusDot / 折叠态视觉
  - `B` = 浮窗右键菜单 / Rust menu
  - `C` = 展开/折叠 状态机 + 输入框 + taskTitle
  - `D` = Rust 黑边 / WebView2 transparent 配置
  - `E` = 浮窗位置 / 尺寸
  - `F` = 浮窗 active session 控制(Pause / Resume / Complete)
  - `G` = 历史任务切换编号（旧 V0.2.1 方案已 superseded，不作为现行验收项）
  - `H` = Pomodoro / Notification(V0.2.2)
  - `I` = 主窗 Style Guide(V0.2 沿用 V0.1.6)
  - ...
- **序号** = 在类目内的顺序, **跨 PATCH 沿用, 新增项递增**(`A-1` `A-2` `A-3` ...)
- **修饰符**:
  - `-1` 后缀 = 该项的"修正版期望", 表示原始期望错了, 这是 user L3 实测后的修正:
    - `[C-3]` = 原始期望, 用 `[C-3 ✗]` 标未通过
    - `[C-3-1]` = 修正后期望, 用 `[C-3-1 ✓]` 标通过
  - **不重复编号**: 修正版不分配新编号, 直接 `-1` 后缀(`C-3` → `C-3-1`)
  - **不用 `'` 引号/prime 符号**: 改用 `-1` 后缀对齐"使用 -1 序号"原则, 视觉噪声更小

### 2.2 验收状态符号

| 符号 | 含义 |
|---|---|
| `✓` | 通过 (L1 + L2 + L3 全部 PASS) |
| `✗` | 未通过 (任何一层 FAIL) |
| `△` | 部分通过 (L1/L2 通过, L3 部分) |
| `⊘` | 不适用 (此 PATCH 不涉及) |

- L2 fail = PATCH 不收口, 必须立即修, 不进 L3

## 五、L3 user 重测(D:\ 端, user 必走)

### 5.1 user 重测流程

1. **同步**: D:\ 端 `git -C D:\workspace\mindtap pull origin develop`
2. **重启 dev.bat**: WebView2 / tauri.conf.json 改动需要重启 WebView2(`Ctrl+C` 终止 dev.bat 重启)
3. **逐项实测**: 按 §2.3.1 验收项列表, 每项标 `✓` / `✗` / `△`
4. **反馈格式**: 按 §2.3.3 L3 user 重测反馈格式(用 `[类目-序号 ✓/✗]`, 不用 "了")
5. **agent 修正**: user 反馈后 agent 进入下一轮 PATCH 修复, 走 L1 → L2 → push origin/develop → 通知 user

### 5.2 L3 失败处理

- L3 fail = 立即开下一 PATCH(V0.2.0.x+1)
- L3 fail 不能仅靠 agent 单方面 commit message claim 已修
- L3 fail 项的 commit message 必须引用 user L3 反馈原话 + PATCH 号

### 5.3 user 改主意处理(C-4 类)

> 真实场景: user L3 实测发现原 PRD 期望错了(如 V0.2.0.13 PATCH C-4 "active session 保持展开", user L3 改主意要"折叠 + ControlRow active")
>
> 处理流程:
> 1. 标原验收项 `✗ + 期望错` (e.g. `[C-4 ✗] active session 保持展开 — 期望错`)
> 2. 标 prime 版期望 `✓` (e.g. `[C-4-1 ✓] active session 折叠 + ControlRow active`)
> 3. **修正该 PATCH 对应的 L0 PRD**（现行 `docs/prd/` 入口）反映 user 改主意
> 4. **修正对应 L3 design**（现行 `docs/design/` 入口）反映 user 改主意
> 5. **修正对应 L2 tech**（现行 `docs/tech/` 入口）反映 user 改主意
> 6. 新 PATCH commit message 注明 "L3 user 改主意, 修正 [C-4] → [C-4-1]"

## 六、反模式 14/15/16/17/18 自查表(PATCH 收口必走)

| 反模式 | 描述 | 防御手段 |
|---|---|---|
| **14 反复修** | 同一个 issue 跨 N 个 PATCH 都未真修 | L1 锁住测试 + L3 user 重测, PATCH 收口必须 N=0 反复 |
| **15 commit 谎改** | commit message 声称已修, 实测未修 | L3 user 重测为唯一真相, agent commit 必须引用 L3 反馈 |
| **16 测试字面断言** | regex 锁源码字面量, 重构即 break | 行为断言(组件树 / API 调用 / 渲染输出)优先 |
| **17 gh/MCP 滥用** | 用 gh CLI / GitHub MCP 跳过 web PR | 纯 git + ssh + web PR(https://github.com/ahajason/mindtap/compare/develop...<branch>) |
| **18 CSS regex 嵌套** | 写 regex 锁 CSS 时没剥 @media/@supports/@keyframes 嵌套块 | 静态扫描前先剥嵌套块, 避免后加的 @media 内嵌同名 selector 误匹配 |
