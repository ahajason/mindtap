# UI 与原生窗口回归收口流程

> **状态**：active
> **适用范围**：UI 样式错乱、透明原生窗口、尺寸/焦点/拖动等跨平台边界问题，以及经历多轮症状修复仍重复出现的回归。

## 一、目标

本流程把“发现症状后直接改样式”替换为可重复执行的证据链：

1. 冻结用户可观察需求；
2. 按 ownership 定位根因层；
3. 建立能在旧实现判红的生产契约；
4. 只修改证据指向的 owner；
5. 删除失效和重复测试；
6. 依次通过结构、工程和目标平台实机验证。

报告负责记录历史证据；本流程只维护以后如何执行。功能的具体尺寸、token 和状态仍属于各自 PRD、Tech、Design，不在这里复制。

## 二、开始前：冻结基线与需求

### 2.1 基线 gate

- 确认当前工作分支包含最新开发基线。
- 记录工作树状态和最近提交，避免把旧快照当生产现状。
- 并行工作产生多个分支或工作树时，先整合再分析；不得从不同基线拼结论。

### 2.2 需求 gate

只写用户可观察事实：

- 用户做什么；
- 用户看到什么；
- 哪些结果明确禁止；
- 哪个真实平台负责最终验收。

尺寸、状态数量、交互结果出现冲突时，先修正唯一 PRD，再修改实现。历史报告不能覆盖当前需求。

## 三、按层归因

| 事实或症状 | 默认 owner | 禁止的跨层绕法 |
|---|---|---|
| 原生窗口尺寸、透明、阴影、焦点 | 原生窗口配置与平台命令 | 用 CSS 尺寸、透明度或阴影模拟 |
| UI 状态和内容可见性 | 应用状态与公共组件行为 | 用 CSS 独立创造第五种状态 |
| 排版、颜色、模糊、圆角 | CSS 与共享 token | 用组件内联样式建立第二材质 owner |
| 原生菜单、拖动、系统快捷键 | 平台 API | 用页面元素模拟系统窗口能力 |
| DPI、合成黑边、聚焦边缘 | 目标平台 compositor | 用 DOM 测试宣称视觉已通过 |
| 测试中的缺字段、缺 export、泄漏 mock | 测试基础设施 | 修改生产逻辑迎合错误 fixture |

归因不明确时，先构造最小观测：生产配置、公共 DOM、平台调用参数、实机截图四者中，哪一层最先偏离契约，哪一层就是首个修复点。

## 四、生产契约先判红

测试只建立在以下 seam：

1. **生产 artifact**：直接读取真实配置、CSS、共享 token 和平台命令注册；
2. **公共 UI 行为**：从用户动作观察可见内容与状态转换；
3. **平台调用边界**：断言发送给原生层的命令和参数；
4. **目标平台实机**：验证 compositor、DPI、焦点和拖动手感。

禁止：

- 在测试里重写一份 CSS 再断言它；
- 用源码公式或精确 class 顺序代替公共行为；
- 在不加载生产 CSS 的 DOM 环境中宣称视觉正确；
- 没有 assertion 的轮询 callback；
- 用不完整 fixture 制造假红。

若旧实现无法让新契约判红，说明 seam 或断言无效，不进入产品代码修改。

## 五、最小根因修复

1. 只修改失败证据指向的 owner。
2. 同一事实存在多个 owner 时，优先删除重复 owner，而不是增加优先级覆盖。
3. 修复后先重跑最窄测试，再跑功能专项。
4. 测试基础设施修正后若生产契约已通过，不继续修改产品代码。
5. 目标平台才可观察的事实，不在本地模拟环境中猜测最终参数。

## 六、测试收口

每个保留测试必须对应一个独立故障模式，至少满足一项：

- 锁定生产 artifact 不变量；
- 覆盖用户关键路径；
- 覆盖高风险状态分支、键盘或可访问性；
- 覆盖平台调用参数或错误降级。

删除或合并：

- 按 PATCH/版本编号永久堆积的叙事测试；
- 依赖是否存在、源码公式、精确 DOM child 顺序等实现耦合断言；
- 已被关键路径覆盖的薄组件渲染测试；
- happy-dom 无法证明的像素级视觉断言；
- 多个文件重复验证的同一配置字段。

测试文件按稳定职责命名，例如 `*.window-contract.test.*` 和 `*.behavior.test.*`，不用历史修复编号命名。

## 七、分层验证

### L1：功能契约

- 生产配置、公共状态、CSS ownership 和平台调用参数通过；
- 专项测试无未处理异常、缺 export、`NaN` 或泄漏 mock；
- 测试数量和删除理由有记录。

### L2：工程回归

- 全量单测；
- 类型检查；
- 生产构建；
- 原生端编译检查。

环境故障必须附最小复现和临时验证方式，不得修改产品代码绕过本机工具链问题。

### L3：目标平台 hard gate

- 记录所有业务状态基准截图；
- 覆盖支持的 DPI/缩放档位；
- 验证物理尺寸、位置、拖动、焦点、原生菜单和重启恢复；
- 验证聚焦与未聚焦的合成边缘。

没有 L3 证据时，完成状态只能写“代码与静态验证完成，视觉待实机验收”。

## 八、文档收口

- PRD 只维护用户可观察需求；
- Tech 维护 ownership、接口、不变量、test seams 和 DoD；
- Design 维护视觉、交互、token 引用和可访问性；
- Report 记录根因、历史证据和本轮实测结果；
- Governance 维护本流程，不复制功能参数。

被完整吸收且会误导的旧入口直接删除；仍有证据价值的旧资料明确降级。历史报告保持原貌，不逐份回写。

## 九、完成判定

只有以下条件全部满足，才能宣称回归已修复：

- 当前需求无冲突；
- 每个关键事实只有一个 owner；
- L1 和 L2 通过；
- L3 目标平台证据通过；
- 失效测试与误导入口已清理；
- 根因报告记录实际结果和剩余限制。
