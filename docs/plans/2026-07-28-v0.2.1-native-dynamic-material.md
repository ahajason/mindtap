# V0.2.1 平台原生动态材质 — 实施计划

> 本计划只安排候选调研、单候选接线、分层验证和证据记录。需求、技术边界与视觉通过条件分别以对应的 PRD、Tech、Design 为准。

## 一、前置 gate

- [ ] 当前 `develop` 基线已核对；
- [ ] V0.2.0 浮窗 L1/L2 回归通过，Windows 顶部边缘结论已明确；
- [ ] 当前 Windows 11 / WebView2 实机环境可用；
- [ ] 每位执行者只使用同一基线收集候选结论；
- [ ] 已建立与候选接线、single owner、fallback 相关的生产契约测试。

## 二、阶段 1：能力盘点与基线证据

1. 读取锁定的 Tauri 版本、Cargo 依赖树和公开 API，确认内建 `windowEffects` 的配置字段、Acrylic/Mica 可用性、Windows 版本限制及启动时接线位置。
2. 检查现有 `floating` 配置、CSS fallback 和 React 根组件，列出材质 owner；确认无第二个背景、模糊或阴影 owner。
3. 在未接原生候选前记录 CSS fallback 的 Windows L3 基线：四状态、背景类型、焦点、100% / 125% / 150% DPI、拖动、resize、右键菜单和不抢焦。
4. 把盘点结论和基线截图写入独立 L5 报告；不能以源码阅读或 Windows 以外环境替代。

**退出条件**：能明确写出第一原生候选的最小接线，并证明 fallback 独立可用。

## 三、阶段 2：Acrylic 单候选验证

1. 先为第一候选新增/调整生产 artifact 契约，让旧实现可判红；契约只验证接线范围、owner 唯一和 fallback 存在。
2. 仅在 `floating` 接线第一候选；不改主窗口、四状态、拖动、菜单、焦点、尺寸或 token。
3. 先运行 L1 最窄契约测试，再运行 L2 全量工程回归。
4. 同一 Windows 环境完成完整 L3 矩阵，并记录所有淘汰信号。
5. 通过则记录其为拟选生产方案并进入阶段 5；未通过则恢复 CSS fallback，复验 fallback 后进入阶段 3。

## 四、阶段 3：Mica 单候选验证

仅当 Acrylic 未通过时执行：

1. 确认上一候选接线已完全移除，fallback 已恢复且通过基础 L3；
2. 使用同一契约和同一 L3 矩阵验证 Mica；
3. 通过则进入阶段 5；未通过则恢复 fallback，并决定是否满足阶段 4 的网页候选准入条件。

## 五、阶段 4：React 候选（条件阶段）

仅在两个原生候选均未通过，或网页候选已有同矩阵明确更优证据时执行：

1. 记录 React 19、构建链、许可与透明 WebView2 的兼容性证据；
2. 引入最多一个候选，且明确其唯一表面 owner 和初始化/渲染失败后的单向 CSS fallback；
3. 对 360×36 折叠几何、拖动、原生菜单、不抢焦、100% / 125% / 150% DPI 逐项验证；
4. 完成完整 L1/L2/L3；任何准入或淘汰条件失败即移除候选，不留半接线路径。

## 六、阶段 5：收口与发布判定

1. 将最终选择、每个淘汰候选、Windows 环境和截图索引写入 L5 验收报告；
2. 再次审查原生生产 owner、CSS fallback owner 和运行期选择不存在重叠；
3. 执行 L1、L2 和最终 Windows L3；
4. 只有选定生产方案完整 L3、CSS fallback 基础 L3 同时通过，才能更新任务状态与 release notes。

## 七、禁止事项

- 不并行接线多个候选；
- 不以 Vitest、构建或静态 CSS 宣称动态材质完成；
- 不新增自写 Win32 FFI 或重复原生效果依赖；
- 不把运行期选择做成用户设置或状态切换逻辑；
- 不在 CSS fallback 验证失败后继续比较下一候选；
- 不因材质问题修改 V0.2.0 窗口行为，除非有独立、可复现的 V0.2.0 契约失败证据。
