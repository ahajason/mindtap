# 需求提示词（完整版，2026-08-02 修订）

> 原始提示词经整理修正，并补充用户新增要求。修正说明见文末。

## 一、总体执行原则

1. 第一步优先从业务本质定义拆解确认**失真确认闭环**（ADR-0012）的设计目的、使用场景、价值作用，而非直接改前端触发逻辑；
2. 第二步基于业务定义，反向梳理当前代码实现逻辑，定位偏差点；
3. 第三步对照 V0.2.1 工作台（失真确认气泡）和 V0.2.2 可信台账与复盘（主窗管理、设置页、前台监听）的原始需求，输出修正方案并落地修复。

## 二、第一阶段：业务层深度分析

### 1. 核心分析目标

搞清楚「失真确认气泡 + 待确认结算」这套能力在产品里的原始业务定位：

- 该失真确认动作对应的真实业务行为是什么？代表用户完成了哪一步履约/办结动作；
- 设计该气泡的核心目的：是风险二次校验、任务节点闭环、失真窗口留痕、还是操作不可逆兜底；
- 哪些角色、在哪种操作场景下理应唤起失真确认气泡，哪些场景属于冗余触发；
- 完成确认后，业务侧会发生哪些数据变更（focus_ms 结算 / pending_ms 清空 / 状态流转）、后续联动规则（失真检测冷却 / 跨天兜底 / 空闲自动暂停）。

### 2. 基于业务定义，回答两个关键疑问

1. 为什么主窗口的 `DormantConfirmDialog` 已返回 null（V0.2.2 修订后不再监听事件）？是早期迭代遗留、逻辑判断条件写错、还是对业务场景理解偏差导致的错误实现；
2. 浮窗气泡窗口（BubbleApp）点击无响应、无法弹出气泡的底层根因，是否和失真检测触发条件判断不一致有关。

### 3. 输出交付物

《失真确认闭环业务能力定义 & 现有实现偏差分析》文档，包含：业务本质、合理触发场景、当前逻辑 BUG 点、代码触发入口点位（BubbleApp / useDormantCheck / floating:dormant 事件 / 后端 30s 线程扫描 / DormantConfirmDialog / Review 页面 stale 列表）。

## 三、第二阶段：依据业务结论进行规则修正

### 1. 触发载体规则修正（对标业务 + V0.2.1 工作台 + V0.2.2 需求）

根据业务分析结论锁定唯一合法唤起入口：

- 明确主窗口不属于失真确认气泡合理触发场景，`DormantConfirmDialog` 保持返回 null 状态；主窗口中的待确认操作仅通过复盘页面（Review route）的 stale 列表按钮完成（`handleConfirm` / `handleIgnore`），主窗仅做状态只读展示；
- 修复浮窗气泡窗口（BubbleApp）触发逻辑，满足失真检测条件时正常唤起气泡（询问态 → 5 秒超时自动暂停 → 待确认态），仅保留需求规定的「记入/丢弃」两个确认操作，不臆测驳回等不存在流程。

### 2. 手动触发失真确认气泡（测试辅助功能）

**目的**：为了在不等待冷却阈值（2h）的前提下方便手动验证失真确认闭环的完整流程，增加测试辅助入口。

**要求**：
- 在浮窗（floating 窗口）的列表态（list）中，对每张进行中/待办任务卡增加一个显式操作入口（如小图标按钮或长按菜单），点击后**立即触发该任务的失真确认气泡**（跳过冷却检测，直接进入 BubbleApp 询问态）；
- 该入口仅用于测试/调试目的，不影响正常业务逻辑——不改变冷却检测的正常触发路径；
- 气泡弹出后的交互（5 秒超时自动暂停 → 待确认态 → 记入/丢弃）与正常失真确认完全一致；
- 该功能可用编译时 flag 或运行时开关控制，避免在生产构建中暴露。

### 3. 设置页面增加失真检测周期控制（V0.2.2 P6 设置页扩展）

在设置页（SettingsPage）中增加以下可调参数，持久化存 `app_setting` 表：

| 参数 | 默认值 | 说明 |
|---|---|---|
| 冷却阈值（失真检测触发间隔） | 2 小时 | 任务无操作超过此阈值即触发失真确认气泡 |
| 空闲自动暂停超时 | 10 分钟 | 系统检测到空闲超过此阈值自动暂停进行中任务并挂待确认 |
| 失真检测轮询间隔（前端） | 5 分钟 | 浮窗气泡窗口轮询 `item_check_dormant` 的间隔 |
| 后台线程扫描间隔 | 30 秒 | 后端 30s 线程执行空闲检测 + 失真检测 + 前台监听（若有）的执行周期 |

**交互要求**：
- 设置项以「分钟」为单位输入，前端做合理范围校验（如冷却阈值 ≥ 30 分钟，空闲超时 ≥ 1 分钟等）；
- 修改后即时生效，不要求重启应用；
- 提供「恢复默认值」一键重置。

### 4. 任务级个性化配置能力的评估（可选，需评审）

基于业务使用诉求，**评估**新增设置项的合理性：

- 在全局设置或任务详情内增加开关：本任务是否需要跳过失真确认气泡（直接自动暂停，不弹气泡询问），用户可自主开启/关闭，配置持久化存 `app_setting` 表；
- **注意**：此方案与 ADR-0012「失真确认闭环」的原始设计意图（系统主动询问，用户判定权不抹除）存在张力，需先评审再落地。

### 5. 文案体验优化

基于业务含义，全盘优化气泡标题、提示文案、按钮文字，确保用户一眼理解本次「继续/暂停」或「记入/丢弃」究竟对应什么业务动作，消除认知歧义。

## 四、主窗删除按钮展示层级优化（V0.2.2 P4 范围）

### 现状

主窗管理页面（ManagePage）列表直接平铺展示大量「删除」按钮，视觉权重过高，干扰常规办公浏览，极易误触。

### 整改目标

完整保留删除功能，仅调整展示层级：移入列表项右上角「更多操作」三点下拉菜单内，默认隐藏不外露；点击菜单内删除选项后，增加二次确认 toast 带撤销（5 秒窗口，sonner），超时后软删除进入回收站；下拉菜单 UI、交互沿用系统现有组件规范，保持统一体验。

## 五、关于「活动监听」的重新评估要求

### 背景

V0.2.2 原始设计文档（ADR-0014 / P5 前台监听）定义了**活动信号与智能提示**功能：

> 前台应用监听（`foreground.rs`），检测前台应用变化，10 分钟未计时 → 浮窗视觉强化 + 建议文案「看起来你在做 X，要记一下吗？」；一键确认建卡 / 一键忽略；打扰级别可配、可全局关。

### 评估要求

Agent 需要重新评估以下问题，并给出结论：

1. **含义澄清**：该功能是否就是「检测用户当前在用什么软件（如 Chrome / VS Code），如果长时间未记录就提示建卡」？与产品北极星「3 秒记录、1 秒查看、0 思考成本」的关系是什么；
2. **必要性判断**：该功能是否与 Mindtap 的核心场景（个人工作台账，用户主动记录）一致，还是属于过度设计/超前需求；
3. **用户价值 vs 实现成本**：Windows 端需要 `GetForegroundWindow` + `GetWindowModuleFileNameW` API，macOS 端需预留；涉及隐私感知（用户可能不想被监听）；30s 轮询有性能开销；
4. **替代方案**：如果不做前台监听，是否有更轻量的方式达到类似目的（如基于失真确认闭环的「冷却检测后反问」已经覆盖了类似场景）。

**输出**：一份简短的评估结论，决定「保留 / 降级为可选设置/ 延后到 V0.2.3+ / 彻底废弃」，并给出理由。

## 六、必须同步一并修复的遗留问题

1. **主窗 ↔ 浮窗 ↔ 气泡窗口跨窗口实时通讯问题**：任意一端修改任务状态、配置、执行失真确认操作，所有已打开窗口自动同步刷新视图，确保数据一致性；
2. **设计指南页面（Style Guide）补充返回按钮**，实现从指南页一键返回主窗（`/style-guide` → `/`），补齐页面跳转闭环；
3. **全量回溯 V0.2.1 工作台 + V0.2.2 可信台账与复盘 Spec**，所有交互不合理、体验割裂、私自超需求开发的内容统一整改，需求模糊点先评审再开发。

## 硬性约束重申

- **失真确认气泡模块**：先业务拆解→再逻辑溯源→最后代码修改，严禁直接删除/注释代码；
- 全程不新增原始需求未提及的操作节点（如驳回、退回等）；
- 所有改动可追溯到业务价值与 V0.2.1 工作台（失真确认闭环）和 V0.2.2 可信台账与复盘（主窗管理、设置页、前台监听）的原始设计文档；
- **测试辅助功能（手动触发气泡）** 仅用于调试，不可影响正常业务逻辑路径，建议用编译时 flag 或环境变量隔离。
