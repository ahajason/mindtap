# ADR 0013: 重复捕获 = 轻提示不阻止,不自动合并

- **状态**: ✅ 已采纳
- **日期**: 2026-08-01
- **决策者**: 用户 + Claude Code(grill 对齐,用户视角澄清)

## 背景

同名任务的重复捕获,存在三种不同性质:

1. **同一天同一件事的延续**(捕「写周报」,下午又捕「写周报」)——用户期望接着原来那张卡;
2. **跨天同名任务自然重开**(「改方案」第二天继续)——应新建,自动合并反而错;
3. **同名但其实是不同任务**(0 思考成本捕获,「写代码」今天 A 项目、昨天 B 项目)——绝不能合并,否则计时/备注全搅一起。

关键洞察: 用户**自己都分不清「同名」是哪种**——因为产品要求 3 秒捕获、无分类、无标题决策,他根本没机会给任务起足够区分的名字。所以产品侧不能武断合并,也不能完全不管。

## 选项

### A: 允许重复并存,不做任何处理
- 优点: 实现最简
- 缺点: 纯误触重复回车(同瞬间按两次)无提示,用户不知道「多了张空卡」

### B: 重复复用旧卡(检测同名→合并/复用)
- 优点: 省重复捕获
- 缺点: 引入合并语义,与 PRD「轻提示不阻止」的「不阻止」字面冲突;会毁掉类型③(同名不同任务被搅一起)

### C: 轻提示不阻止(PRD §8 边界原文)
- 优点: 承认「同名 = 同一件事」无法可靠判断,不打断 3 秒捕获;把判断交还用户
- 缺点: 同名卡会并存(但符合 PRD)

## 决策

选了 **C: 轻提示不阻止,不自动合并**。

- create 时检测同名已有 active / 收件箱 / 待办 → 返回轻提示信号;
- 前端不阻止,只用极轻视觉提示(如同一名小圆点),判断交还用户;
- 跨天由 auto-pause 自然分开,重开即新卡。

## 反向后果

如果选错了(用户其实期望自动合并),同名卡并存会让列表略多、需手动清理。但「轻提示不阻止」是 PRD 原文,且合并语义的破坏性(类型③)远大于手动清理成本。未来若多数用户期望合并,可升级为「轻提示 + 一键合并」的显式动作,而非静默合并。
