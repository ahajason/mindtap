# ADR 0011: Item 统一实体取代 timer_session(含表迁移决策)

- **状态**: ✅ 已采纳
- **日期**: 2026-08-01
- **决策者**: 用户 + Claude Code(grill 对齐)

## 背景

V0.2 阶段把「任务记录」建模成独立的 `timer_session` 实体,只有「进行中 / 暂停 / 已完成」3 态,且**全局唯一 1 个进行中**。产品需求文档演进后,工作台账方向要求:

- 全产品只有一张表、一套存储、一个列表入口(PRD §3.1);
- 任务族支持**多并行进行中**(PRD §1.2 / §3.2);
- 五态状态机(收件箱 / 待办 / 进行中 / 完成 / 归档);
- 生活记录(速记族)与工作待办是同一实体,区别只在类型。

继续用独立 timer_session 无法表达这些,必须把实体演进为统一的 **Item**。

## 选项

### A: 建新表 `item`,旧 timer_session 表遗留不动
- 优点: 无数据风险、可回退
- 缺点: 两张表并存,存储不统一,违背「全产品只有一张表」;旧 active 数据无法并入新状态机

### B: 建新表 `item` + DROP 旧表 timer_session
- 优点: 干净,单一存储,符合「全产品一张表」
- 缺点: **破坏性**——存量 timer_session 数据丢失

### C: 建新表 `item` + 一次性迁移脚本迁旧数据
- 优点: 保留存量数据
- 缺点: 多一笔迁移工作量;旧 3 态(active/paused/completed)与新五态语义映射不自然

## 决策

选了 **B: 建新表 `item` + DROP 旧表 timer_session**。

- 依据: 当前 `timer_session` 存量数据是开发测试数据(无真实用户数据),破坏性可接受;
- 用户显式确认了这一破坏性决策(grill 对齐点 2);
- 迁移成本(选项 C)的收益在当前阶段趋近于零。

## 反向后果

如果选错了(实际存在真实用户数据时仍 DROP),会丢失用户的历史记录,违背「全量本地存储」基因。**未来若进入真实用户阶段,必须改为带迁移的演进,不再 DROP。** 这是一个已明确定界的决策,不是通用先例。
